# Repro HCI study protocol

Version 0.2, 2026-10-15. **Planned; zero participant sessions.** This protocol does not authorize recruitment, contact, recording or collection. Its [research question](HCI-RESEARCH.md) concerns whether developers distinguish supported reproduction/fix claims from unsupported ones. The [version 2 blank materials](../research/hci/README.md) support preparation of the planned assignments and measures; they contain no completed records or approvals.

## Start gates and study stages

Before contact or collection, the responsible human study owner must approve the protocol, recruitment/compensation, consent language, data handling and applicable institutional ethics review or exemption determination. Record the actual determination; do not self-declare exemption. Participation is voluntary, may stop without penalty, and must not affect employment or course assessment. Agree accessibility accommodations before scheduling.

Use a synthetic, local task environment without participant repositories, credentials or browser profiles. Collect only a random participant code, coarse relevant debugging experience, task answers, confidence and task-scoped interactions. Do not collect employer/client names or unrelated screen content. Notes are the default; optional audio/screen recording requires separate informed opt-in and must remain limited to the study window. Consent/contact records stay separate from research data. A human owner must set access, storage, retention/deletion dates, withdrawal procedure and permitted reporting before the first session. No participant data belongs in this repository, Git, Library, telemetry or an external model. Portable materials may contain the empty templates and synthetic task specification only.

1. **Preparation:** freeze builds, evidence and scoring key; inspect both conditions; conduct a researcher walkthrough without inventing participant records. Current source review is not this interactive walkthrough.
2. **Formative study, proposed 6–8 developers:** inspect the existing workbench using the tasks below, with think-aloud and neutral prompts. Find confusing language and navigation; revise materials. This small convenience sample is for diagnosis, not an effect-size claim.
3. **Comparative study, proposed 16 developers:** an exploratory balanced comparison after candidate and comparator implementation and fidelity checks. The number is a planning choice, not a power calculation. A confirmatory study requires a separately frozen sample-size justification using pilot variability and a meaningful error-rate change, preregistration, and broader tasks.

Recruitment has not begun. Eligibility should be adults who have debugged a JavaScript/TypeScript web application; sample a range of relevant experience and tool habits rather than changing eligibility after observing low performance. Do not exclude difficulty, low scores, disability or slow use after the fact. Report the recruited population and limits honestly.

## Conditions, counterbalancing and fidelity

**P:** task-focused workbench candidate, Establish failure → Reduce steps → Check fix, with connected reduction explanations and progressive disclosure. **L:** conventional readable, searchable evidence/log report containing the identical backend results, manifests, trial decisions, identity values and uncertainty. It must have ordinary headings, navigation/search, keyboard access and readable formatting; it is not an intentionally inconvenient wall of text. Both get the same glossary, evidence access and training time. The six-section UI was the implementation baseline. P now has an initial implemented question sequence, persistent expectation and connected trial inspector with technical checks; it is not yet a frozen study condition. A research-only P adaptation and L report now render the same 74 source-linked facts from five actual records of the frozen synthetic release case. Their bounded keyboard, recovery, search, responsive and Axe rehearsal is recorded in [HCI-FIDELITY](../evidence/HCI-FIDELITY.md). This does not freeze the live product as a study condition or establish human usability, broader task-set equivalence, native zoom or screen-reader behavior.

The primary comparison concerns **inspection and decisions on precomputed real synthetic runs**. Do not give one condition a live runner and the other only screenshots. Both receive the same fixed files and observations, with trial/record identities bound in a case manifest. Live capture, cancellation and reconnection are a separate formative workflow module, excluded from the inspection timing comparison. A static prototype can test interpretation but cannot establish execution/recovery usability.

Prepare two matched case sets, A and B, each containing conclusive, incomplete/cancelled and historical-selection cases. Assign participants in randomized blocks to four sequences: P/A → L/B; L/B → P/A; P/B → L/A; L/A → P/B. Preserve the randomization seed and assigned sequence before outcomes are collected. Use a different practice case, neutral condition names, and no correct-answer feedback between scored blocks. Balance supported/unsupported claim presentation order within each set. If case sets contain different bugs, cross each case with both conditions across participants.

Currently only one failure family is implemented. New run IDs are not independent tasks. Reusing the same Alpha/Beta bug in A and B risks learning the answer, even with counterbalancing. Such a comparison is only a feasibility/learning study; do not claim general interface superiority. Broader comparison requires eligible independently verified case families and matched difficulty, not cosmetically renamed or invented observations.

Before each study build is frozen, two reviewers must verify: same source/run digests and answer content across P/L; no hidden extra hints or missing limitations; identical case selection and available operations; accurate synthetic labels; no network/telemetry; readable long values; keyboard navigation and accessible status. Record viewport, browser/version, native zoom, input mode, build hashes, fixture/manifest/assertion/harness identities and task order. Recheck after any change; preserve earlier build data separately. Native Chrome navigation and 200% zoom remain gated in the current host; do not bypass that restriction to satisfy this protocol. Screen-reader usability is unrun.

## Claim judgments and measures

After each scored inspection task, present only its claims from the frozen task/claim schedule and ask: “Is this claim supported by the supplied evidence: yes, no, or unsure?” Then ask for a 0–100 estimate that the claim is supported and a one-sentence reason with an evidence reference. The following keys refer only to the historical schema-1 inspection case above. These are task-specific measures, not a validated general trust questionnaire.

| Claim ID / selected evidence | Claim | Key |
| --- | --- | --- |
| C1 / original conclusive run | The intended stale-response failure reproduced under this experiment's inputs. | Yes |
| C2 / valid comparison | The registered candidate satisfies the same bounded frontend requirement. | Yes |
| C3 / valid comparison | A fix to the real search backend has been verified. | No |
| C4 / accepted reduction | The retained smaller input preserved the target failure in the required repeated trials. | Yes |
| C5 / reviewed reduction | This is the globally smallest possible failing input. | No |
| C6 / reviewed reduction | Every retained step has been shown necessary by a conclusive deletion experiment. | No |
| C7 / cancelled baseline | This cancelled run supplies a newly verified reduction baseline. | No |
| C8 / earlier record selected | The selected record contains the later candidate verification result. | No |
| C9 / finalized export | A local capsule directory has been finalized for the displayed export job. | Yes |
| C10 / export alone | The capsule has therefore already passed clean-machine replay. | No |

**Primary outcome:** false acceptance = Yes on an unsupported claim, divided by answered unsupported claims per participant/condition. Report the denominator, missingness and unsure separately. Also report false rejection = No on supported claims, supported claims withheld as unsure, and correct supported acceptance. An all-No strategy must not appear as a successful interface.

**Understanding:** score each of six concepts 0 = incorrect/absent, 1 = correct partial, 2 = correct with linked evidence: expected vs observed behavior; input/response order; real vs mocked boundary; reduction vs necessity/minimality; same-assertion bounded comparison; selected-run identity vs export/portability. Use the task key and preserve the rationale for partial credit. The version 2 blank materials preserve each concept score, its evidence and coder/pass identity against the original task attempt; an unscored concept remains blank, not zero. Two coders independently score a preregistered subset, resolve discrepancies transparently, and report agreement before adjudication. Preserve both independent passes and use separate adjudication records referencing them; never overwrite the original scores with agreement. Prefer answer-only coding with interface identity removed when feasible.

**Calibration:** for answered claim j, let p be the stated support probability divided by 100 and y its key (0/1). Report mean `(p-y)^2`, average confidence for correct/incorrect judgments, and confidence distributions by supported/unsupported claim. This measures correspondence to the case key, not universal trustworthiness; validate that participants understand “supported” first.

**Task and recovery:** record independent/assisted/partial/failed completion, withdrawal or technical interruption, active inspection time, time to first correct evidence, navigation/disclosure/search count, wrong-job attribution, unsupported-success inference, missed mock/minimality limit, help requests and recovery success/time. Define a 4-minute inspection limit per task before pilots; revise and freeze it in the task schedule before comparison. Record explicit ending reason separately from completion. In the blank forms and [analysis contract](../research/hci/ANALYSIS-CONTRACT.md), `censored` means **administrative timeout only**: a partial/failed task ending at its time limit has `censored=true` and elapsed time exactly equal to the frozen limit. Independent/assisted completion, earlier stopped-incomplete work, withdrawal and technical interruption have `censored=false`; retain measured active time, or a missing value if unmeasured. Never replace an early ending with the limit or count a timeout as completion. This bookkeeping convention does not assert a survival-model interpretation of other endings. Record service faults/latency separately. Fewer clicks or reruns do not on their own mean better usability. Ask a brief ease rating and an open debrief question; preference does not replace correctness.

## Session and analysis discipline

Use equal tutorials and a practice task, then two timed inspection blocks, claim judgments, and a short retrospective interview (approximately 45–60 minutes, adjusted and frozen after preparation). Use think-aloud only in the formative study; the comparison uses the same silent-work/retrospective procedure in both conditions. Facilitator prompts may clarify task wording but must not suggest which evidence to inspect. Log every intervention.

Prepare the version 2 blank session manifest with both planned blocks, each block's condition, order, case/evidence identities, and explicit frozen task and claim slots, including task limits, claim presentation order and case-bound scoring keys. This expected-slot schedule must exist before any observations so an unanswered scheduled item stays distinguishable from an unassigned one. Link task attempts, claim judgments and coding records to the exact participant manifest/block/slot and preserve original attempt identity. Retain retries separately; never silently replace the original result with a later or better attempt. These are blank preparation contracts, not approval to populate them. The offline synthetic analyzer still accepts only its declared synthetic test schema, with one observation per scheduled slot; the forms add no human-data import mode.

Preregister primary outcome, task key, sample/stopping plan, order scheme, exclusions and analysis before comparative collection. Analyze paired participant-level differences with uncertainty intervals; do not treat multiple claims from one participant as independent people. Report item, experience and order effects descriptively and check first-block results for learning sensitivity. Keep incomplete sessions and tool failures visible; document any excluded item using a rule set before outcomes are examined. A small exploratory sample cannot establish equivalence from a nonsignificant result. Any confirmatory model/power plan must be specified before its data are collected.

Reproducibility package: protocol/version, task prompts, de-identified case manifests, exact build and evidence hashes, condition implementation/source, assignment algorithm/seed, scoring codebook, blank forms, and an analysis script tested on clearly labeled nonparticipant test inputs.
