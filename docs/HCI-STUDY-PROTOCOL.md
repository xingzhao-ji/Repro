# Repro HCI study protocol

Version 0.1, 2026-10-13. **Planned; zero participant sessions.** This protocol does not authorize recruitment, contact, recording or collection. Its [research question](HCI-RESEARCH.md) concerns whether developers distinguish supported reproduction/fix claims from unsupported ones. [Blank materials](../research/hci/README.md) contain no completed records.

## Start gates and study stages

Before contact or collection, the responsible human study owner must approve the protocol, recruitment/compensation, consent language, data handling and applicable institutional ethics review or exemption determination. Record the actual determination; do not self-declare exemption. Participation is voluntary, may stop without penalty, and must not affect employment or course assessment. Agree accessibility accommodations before scheduling.

Use a synthetic, local task environment without participant repositories, credentials or browser profiles. Collect only a random participant code, coarse relevant debugging experience, task answers, confidence and task-scoped interactions. Do not collect employer/client names or unrelated screen content. Notes are the default; optional audio/screen recording requires separate informed opt-in and must remain limited to the study window. Consent/contact records stay separate from research data. A human owner must set access, storage, retention/deletion dates, withdrawal procedure and permitted reporting before the first session. No participant data belongs in this repository, Git, Library, telemetry or an external model. Portable materials may contain the empty templates and synthetic task specification only.

1. **Preparation:** freeze builds, evidence and scoring key; inspect both conditions; conduct a researcher walkthrough without inventing participant records. Current source review is not this interactive walkthrough.
2. **Formative study, proposed 6–8 developers:** inspect the existing workbench using the tasks below, with think-aloud and neutral prompts. Find confusing language and navigation; revise materials. This small convenience sample is for diagnosis, not an effect-size claim.
3. **Comparative study, proposed 16 developers:** an exploratory balanced comparison after candidate and comparator implementation and fidelity checks. The number is a planning choice, not a power calculation. A confirmatory study requires a separately frozen sample-size justification using pilot variability and a meaningful error-rate change, preregistration, and broader tasks.

Recruitment has not begun. Eligibility should be adults who have debugged a JavaScript/TypeScript web application; sample a range of relevant experience and tool habits rather than changing eligibility after observing low performance. Do not exclude difficulty, low scores, disability or slow use after the fact. Report the recruited population and limits honestly.

## Conditions, counterbalancing and fidelity

**P:** task-focused workbench candidate, Establish failure → Reduce steps → Check fix, with connected reduction explanations and progressive disclosure. **L:** conventional readable, searchable evidence/log report containing the identical backend results, manifests, trial decisions, identity values and uncertainty. It must have ordinary headings, navigation/search, keyboard access and readable formatting; it is not an intentionally inconvenient wall of text. Both get the same glossary, evidence access and training time. The six-section UI was the implementation baseline. P reuses the implemented question sequence, persistent expectation and connected trial inspector. The offline L report is now implemented with the same frozen packet, job selector, search, glossary and evidence access. Final retained-case fidelity verification is in progress; constructed-fixture browser checks alone do not establish that gate. Neither condition is approved for participant use.

The primary comparison concerns **inspection and decisions on precomputed real synthetic runs**. Do not give one condition a live runner and the other only screenshots. Both receive the same fixed files and observations, with trial/record identities bound in a case manifest. Live capture, cancellation and reconnection are a separate formative workflow module, excluded from the inspection timing comparison. A static prototype can test interpretation but cannot establish execution/recovery usability.

Prepare two matched case sets, A and B, each containing conclusive, incomplete/cancelled and historical-selection cases. Assign participants in randomized blocks to four sequences: P/A → L/B; L/B → P/A; P/B → L/A; L/A → P/B. Preserve the randomization seed and assigned sequence before outcomes are collected. Use a different practice case, neutral condition names, and no correct-answer feedback between scored blocks. Balance supported/unsupported claim presentation order within each set. If case sets contain different bugs, cross each case with both conditions across participants.

Currently only one failure family is implemented. New run IDs are not independent tasks. Reusing the same Alpha/Beta bug in A and B risks learning the answer, even with counterbalancing. Such a comparison is only a feasibility/learning study; do not claim general interface superiority. Broader comparison requires eligible independently verified case families and matched difficulty, not cosmetically renamed or invented observations.

Before each study build is frozen, two reviewers must verify: same source/run digests and answer content across P/L; no hidden extra hints or missing limitations; identical case selection and available operations; accurate synthetic labels; no network/telemetry; readable long values; keyboard navigation and accessible status. Record viewport, browser/version, native zoom, input mode, build hashes, fixture/manifest/assertion/harness identities and task order. Recheck after any change; preserve earlier build data separately. Native Chrome navigation and 200% zoom remain gated in the current host; do not bypass that restriction to satisfy this protocol. Screen-reader usability is unrun.

## Tasks and objective answer key

Keep the answer-key column private to facilitators until debrief. Use the participant prompt without adding the correct concepts as hints. Score the actual case's persisted evidence, not an expected screenshot. The canonical key is grounded in [manifest](../src/manifest.ts), [frozen oracle](../src/oracle.ts), [registered frontend](../fixtures/browser-search/README.md) and the inspected [review snapshot](../research/hci/review-snapshot.json).

| ID | Participant task | Required observations / answer key |
| --- | --- | --- |
| T1, formative workflow | “Before starting this session, explain what will be recorded and where it goes. Start only if that matches the task.” | Scripted registered synthetic loopback fixture; fresh browser context; actions, controlled responses, trace and screenshot; local owned storage; explicit checkbox opt-in and cancellation; no personal profile/upload or arbitrary production capture. Successful opt-in does not itself prove portability. |
| T2, establish failure | “A maintainer asks whether this evidence reproduces the reported failure. Give your conclusion and show the evidence you used.” | Search alpha then beta; request 2/Beta completes before request 1/Alpha. Latest query remains beta and request ID 2. Buggy observation contains `Alpha synthetic result`, violating the frozen latest-response expectation after both responses; one assertion executed. The real frontend handles mocked HTTP responses. A different error or zero assertions would not establish this failure. |
| T3, reduce steps | “Which smaller reproduction can the maintainer use, and what can you conclude about the removed and remaining steps?” | In the selected accepted reduction, five actions become `navigate`, `search-alpha`, `search-beta`; focus-before/after are removed. Accepted changes have repeated evidence of the intended failure and unchanged assertion/schedule. Dependencies are preserved. Rejected/inconclusive deletion attempts establish neither failure preservation nor necessity. Minimality remains unverified in the inspected example; never infer global minimality from three actions or Complete. |
| T4, check fix | “Would you accept this evidence as checking the candidate against the report? State precisely what you would write in the issue.” | Original: target-failure/Alpha; candidate: requirement-satisfied/Beta. | T5, evidence attribution and recovery | “Find the earlier record run, then inspect whether that run includes comparison evidence. Dependencies and the persistent expectation describe the selected job’s saved historical input and its exact digest; they must not silently substitute the current capsule. In the separate live formative module, new operations use the separately labeled current capsule; frozen P/L provide inspection only. An unknown explicit job yields INCONCLUSIVE/NOT_FOUND. Select the valid earlier job; verify its operation/ID, retained selection after refresh/navigation, and expected events. Reconnect alone cannot repair an invalid job ID. |
| T6, incomplete evidence and handoff | “This reduction was cancelled. What result can be used? For the completed export, explain what the maintainer has and what is still needed.” | Inspect the exact cancellation reason: the reviewed case did not establish its new baseline and accepted no trial, so its retained action count is not new reproduction evidence. Prior verified evidence remains a separate run. The completed export records a finalized local capsule, manifest identity and file count. Frozen P/L withhold its machine-specific path and expose the same source-hash-bound readable test and instructions as inert text. The execution bundle is excluded. Do not hard-code timings, trial count or UUID as a correctness criterion. T5 requires a prepared valid/invalid route or report locator in both conditions. Bind the key to the selected job’s input endpoint and manifest digest, as exercised in evidence/HCI-INSPECTOR.md; score historical attribution against that saved input. Preserve source truth when preparing errors: label any deliberately injected recovery data as synthetic; do not turn it into a claimed actual capture. The existing Linux arm64 success is separate technical evidence, not an answer implied by a UI export badge or a human-usability result.

## Claim judgments and measures

After each scored inspection task, ask: “Is this claim supported by the supplied evidence: yes, no, or unsure?” Then ask for a 0–100 estimate that the claim is supported and a one-sentence reason with an evidence reference. These are task-specific measures, not a validated general trust questionnaire.

| Claim ID / selected evidence | Claim | Key |
| --- | --- | --- |
| C1 / original conclusive run | The intended stale-response failure reproduced under this experiment's inputs. | Yes |
| C2 / valid comparison | The registered candidate satisfies the same bounded frontend requirement. | Yes |
| C3 / valid comparison | A fix to the real search backend has been verified. | No |
| C4 / accepted reduction | The retained smaller input preserved the target failure in the required repeated trials. | Yes |
| C5 / reviewed reduction | This is the globally smallest possible failing input. | No |
| C6 / reviewed reduction | Every retained step has been shown necessary by a conclusive deletion experiment. | No |
| C7 / cancelled baseline | This cancelled run supplies a newly verified reduction baseline. | No |
| C8 / earlier record selected | The selected record contains the later candidate verification result. | No |
| C9 / finalized export | A local capsule directory has been finalized for the displayed export job. | Yes |
| C10 / export alone | The capsule has therefore already passed clean-machine replay. | No |

**Primary outcome:** false acceptance = Yes on an unsupported claim, divided by answered unsupported claims per participant/condition. Report the denominator, missingness and unsure separately. Also report false rejection = No on supported claims, supported claims withheld as unsure, and correct supported acceptance. An all-No strategy must not appear as a successful interface.

**Understanding:** score each of six concepts 0 = incorrect/absent, 1 = correct partial, 2 = correct with linked evidence: expected vs observed behavior; input/response order; real vs mocked boundary; reduction vs necessity/minimality; same-assertion bounded comparison; selected-run identity vs export/portability. Use the task key and preserve the rationale for partial credit. Two coders independently score a preregistered subset, resolve discrepancies transparently, and report agreement before adjudication. Prefer answer-only coding with interface identity removed when feasible.

**Calibration:** for answered claim j, let p be the stated support probability divided by 100 and y its key (0/1). Report mean `(p-y)^2`, average confidence for correct/incorrect judgments, and confidence distributions by supported/unsupported claim. This measures correspondence to the case key, not universal trustworthiness; validate that participants understand “supported” first.

**Task and recovery:** record independent/assisted/partial/failed completion, active inspection time, time to first correct evidence, navigation/disclosure/search count, wrong-job attribution, unsupported-success inference, missed mock/minimality limit, help requests and recovery success/time. Define a 4-minute inspection limit per task before pilots; revise and freeze before comparison. Unfinished tasks are censored at the limit, not completed at that time or removed. Record service faults/latency separately. Fewer clicks or reruns do not on their own mean better usability. Ask a brief ease rating and an open debrief question; preference does not replace correctness.

## Session and analysis discipline

Use equal tutorials and a practice task, then two timed inspection blocks, claim judgments, and a short retrospective interview (approximately 45–60 minutes, adjusted and frozen after preparation). Use think-aloud only in the formative study; the comparison uses the same silent-work/retrospective procedure in both conditions. Facilitator prompts may clarify task wording but must not suggest which evidence to inspect. Log every intervention.

Preregister primary outcome, task key, sample/stopping plan, order scheme, exclusions and analysis before comparative collection. Analyze paired participant-level differences with uncertainty intervals; do not treat multiple claims from one participant as independent people. Report item, experience and order effects descriptively and check first-block results for learning sensitivity. Keep incomplete sessions and tool failures visible; document any excluded item using a rule set before outcomes are examined. A small exploratory sample cannot establish equivalence from a nonsignificant result. Any confirmatory model/power plan must be specified before its data are collected.

Reproducibility package: protocol/version, task prompts, de-identified case manifests, exact build and evidence hashes, condition implementation/source, assignment algorithm/seed, scoring codebook, blank forms, and an analysis script tested on clearly labeled nonparticipant test inputs. The offline synthetic analysis instrument is now implemented and regression-tested; see [its contract](../research/hci/ANALYSIS-CONTRACT.md) and [technical evidence](../evidence/HCI-ANALYSIS.md). It does not implement human-data import, comprehension coding, experience effects or inferential uncertainty intervals. The offline comparator implementation is undergoing final retained-case fidelity verification. Matched independent task sets, human-study rehearsal and the remaining human-analysis work are still pending. The tested product keyboard workflow does not substitute for study-condition fidelity or human evaluation. Publish human records or quotations only within their explicit consent and approval. Preserve null/negative findings and protocol deviations. No conference-readiness or research-success claim follows from technical tests, this protocol, or an agent review.
